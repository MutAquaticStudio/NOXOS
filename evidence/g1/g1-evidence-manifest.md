# NØX-OS Gate 1 evidence contract

This file is a static schema and acceptance contract. It MUST NOT contain current deployment
statuses, mutable provider observations, live run identifiers, or a user-local evidence path.

Per-SHA evidence is generated by GitHub Actions after the required cloud probes complete. The
durable evidence pair is:

1. a GitHub Actions artifact named `g1-staging-evidence-<accepted-main-sha>`; and
2. an annotated Git tag named `g1-staging-accepted-<accepted-main-sha>` that points to that exact
   source commit and names the Actions run and artifact.

The Production pipeline skeleton verifies this exact annotated tag before it can consider a
manually supplied source SHA. It does not trust a mutable environment variable as the acceptance
authority.

The artifact and tag are execution evidence. This source file only defines what they must prove.

## Allowed result states

Every requirement result MUST be exactly one of:

- `PASS`
- `FAIL`
- `NOT_VERIFIABLE`
- `NOT_APPLICABLE`, only when the G1 contract explicitly allows it

References that do not exist MUST use `NONE`; they must never be fabricated.

## SHA-binding rules

- `ciSha` and `previewSha` identify the accepted pull-request head.
- The accepted Preview deployment MUST expose `previewSha` as its immutable source identity.
- `mergedMainSha`, `expectedStagingSha`, and `deployedStagingSha` MUST all identify the same
  accepted `main` commit.
- The associated merged pull request binds `previewSha` to `mergedMainSha`.
- The Staging Vercel deployment MUST expose `deployedStagingSha` through authenticated provider
  read-back and its safe health/version contracts.
- Evidence from an older SHA is historical and MUST NOT satisfy a later candidate.

## Provider acceptance requirements

### Supabase PostgreSQL

- Staging and Production project references differ.
- Staging connects through Supavisor transaction mode using `nox_app_runtime` and
  `nox_workflow_runtime`.
- Live probes return those exact `current_user` values and prove neither role is owner,
  superuser, role creator, database creator, replication-capable, or RLS-bypassing.
- Staging never needs or receives a Production database credential.

### Supabase Storage

Storage identity is `(project_ref, bucket_id)`. The same bucket ID in two distinct projects does
not identify the same resource. Evidence records bucket existence and `public=false` separately,
then proves public read denial and authorized put/stat/read/delete through the Staging project.

### Migrations

The committed `supabase/migrations/*.sql` files are authoritative. Staging evidence requires
dry-run, apply-or-no-op, remote history, and drift verification for the accepted main SHA.

### Durable workflow

The provider identity is `@vercel/queue@0.5.1`, behind the internal `WorkflowLauncher` port.
Staging evidence requires API launch, queue delivery, an intentional durable retry, idempotent
completion, correlation preservation, and a completion write made through
`nox_workflow_runtime`.

### Cloudflare

- The public application remains DNS-only.
- The privileged hostname is proxied only through the explicitly approved Access path.
- Turnstile is verified server-side and is not authentication.
- Access is an edge admission control and is not NØX RBAC.
- One-time sitekey/secret and identity-group bootstrap may occur only in provider/protected secret
  stores; routine reconciliation is automated afterward.

### Final freeze

The Staging artifact is necessary but does not itself freeze G1. A complete A→U DoD audit must
bind its conclusions to the tagged Staging SHA. Only then may the external canonical G1 record
state `GATE_1_STATUS=FROZEN`, `GATE_1_DOD=PASS`, and `G2_READY=YES`.
